# 每日收益报告初步方案

## 目标

每天上午 `09:35`（北京时间；当前服务器时区为 `CST +0800`，因此服务端实际触发时刻也是 `09:35`）自动向 Telegram 发送一条收益报告，内容至少包含：

1. 基于当前活跃借贷估计的“昨天收益”
2. 昨日实际到账利息
3. 最近 `7` 天、本周、本月、本年的实际到账利息汇总

本方案先输出初步设计，用于逐点讨论确认，暂不直接进入最终实现。

## 现状结论

### 1. 当前仓库已有能力

- 已有 Telegram worker 与消息发送通道，可直接复用
- 已有活跃借贷查询：`GetFundingCredits(symbol)`
- 已有新借贷通知逻辑，且已经能根据 active credits 计算“预期收益”
- 已有独立调度器模式，例如：
  - `scheduleMainTask()`
  - `scheduleLendingCheck()`
  - `scheduleHourlyRateCheck()`

### 2. 当前仓库缺失能力

- 没有“历史利息到账记录”查询接口
- 没有“每日固定时刻推送某类报表”的 scheduler
- 没有“报告是否已发送”的持久化去重状态
- 没有“收益汇总服务”这一层抽象

### 3. 关键风险

新增收益报告任务如果直接独立查询 Bitfinex 私有 API，容易与：

- `MainTask`
- `LendingCheck`
- Telegram 手动触发 `/run` `/restart`

发生并发，重新引发此前修复过的 `nonce: small (10114)` 问题。

所以收益报告查询必须纳入现有私有 API 互斥控制，不能裸开新 goroutine 后直接调私有接口。

## 初步方案总览

推荐按“一个收益报告服务 + 一个每日调度器 + 一份去重状态 + 两类收益口径”来做。

### 方案拆分

1. **收益报告服务**
   - 负责组织数据查询、计算、汇总、格式化
   - 对外只暴露“生成报告文本”能力

2. **每日 09:35 调度器**
   - 负责每天到点触发收益报告服务
   - 负责 context 取消、下一次执行时间计算

3. **收益报告发送去重状态**
   - 负责记录“某天是否已发送”
   - 防止 09:35 后服务重启再次重复发送

4. **Telegram 发送复用**
   - 仍然复用现有 `SendNotification`
   - 不单独新造 Telegram 发送链路

## 收益口径设计

这是本需求最关键的地方，建议分成两套数据，不混为一个数。

### 1. 预估收益

定义：**基于两类借贷订单，估计“昨天整天应产生的收益”**

这两类订单分别是：

1. 当前仍然活跃的借贷订单
2. 结束时间落在“昨天”时间窗口内的借贷订单

计算公式：

`出借数量 x 利率 x (出借时间(秒) / 86400) x (1 - 手续费比例)`

其中：

- 出借数量：`credit.Amount`
- 利率：优先 `EffectiveDailyRate()`
- 出借时间：指 **该 credit 在“昨天 00:00:00 ~ 今天 00:00:00”这个时间窗口内实际处于活跃状态的秒数**
- 手续费比例：平台抽取收益的 `15%`，即收益乘以 `0.85`

也就是说，预估收益不是“累计到现在”，而是只估计“昨天这一整天”的理论收益。

进一步说，参与“昨天预估收益”计算的 credit 集合应为：

- 今天 `09:35` 仍然活跃的 credit
- 虽然当前已不活跃，但结束时间落在昨天的 credit

这样可以避免遗漏“昨天还有收益、但今天早上已经结束”的订单。

#### 预估收益示例

假设当前活跃 credit 为：

- `437 x 0.039%`
- `6000 x 0.0301%`
- `4000 x 0.0301%`

且这 3 笔在昨天都完整活跃了 `86400` 秒，则：

`(437 x 0.039% + 6000 x 0.0301% + 4000 x 0.0301%) x 0.85 = 2.7`

这里的 `2.7` 即“昨天预估收益”。

### 2. 实际到账收益

定义：**Bitfinex 实际发放到 funding wallet 的利息记录汇总**

建议来源：

- Bitfinex `Ledgers` 历史账本接口

原因：

- `FundingCredits` 只能看到活跃借贷，不能准确代表历史已到账利息
- 日/周/月/年汇总必须依赖历史账本，而不是当前持仓

#### B-2. ledger 筛选规则比较

`Ledgers` 支持 `wallet` 和 `category` 过滤，三种常见筛法的影响如下：

1. `wallet=funding`
   - 只限定 funding 钱包，范围最安全
   - 但仍可能混入非利息类 funding 账目，噪音偏大
2. `category=...`
   - 直接按账本事件类型筛选，理论上最精准
   - 但对 category 枚举依赖更强，若值没确认或后续变化，容易漏数
3. `wallet=funding + category=...`
   - 范围和类型都收紧，最适合做收益报告汇总
   - 但需要先确认具体 category 值，并保留兜底规则

第一版更建议：

1. 外层先用 `wallet=funding`
2. 内层再按已确认的利息类 `category` 过滤
3. 如果 `category` 还没最终确认，先用 `wallet=funding` + description 规则临时兜底

## 为什么收益报告不能只靠 active credits 覆盖昨天口径

不同来源的作用边界不一样：

1. `active credits`
   - 只能看到当前仍活跃的订单
   - 适合看“现在持仓”，不适合单独做昨天收益对比
2. `Funding Credits History`
   - 可以补齐“昨天结束、今天早上已经不活跃”的订单
   - 只保留最近 3 天，更适合昨日口径，不适合长期统计
3. `Ledgers`
   - 代表实际到账流水
   - 适合做昨日实际到账和 7 天 / 本周 / 本月 / 本年汇总

在展示层上，建议把：

1. 昨天预估收益
2. 昨日实际到账收益

放在同一个对比区块，用于直接观察收益差异。

而下面这些：

- 最近 7 天
- 本周
- 本月
- 本年

放在单独的“汇总数据”区块中。

## 初步实现路径

### 一、数据源层

#### A. 活跃借贷昨天预估收益

需要组合两类来源：

1. 当前活跃 credit
   - `GetFundingCredits(fundingSymbol)`
2. 昨天结束的 credit
   - 需要额外的 `Funding Credits History` 数据源

需要新增的能力：

- 合并“当前活跃”与“昨天结束”的 credit 集合
- 计算每个 credit 在“昨天 00:00:00 ~ 今天 00:00:00”窗口内的活跃秒数
- 按昨天窗口内活跃时长计算收益
- 支持 FRR fallback / `EffectiveDailyRate()`
- 统一按 `15%` 手续费扣减

这里有一个实现上的重要变化：

- 如果只查询当前 active credits，会漏掉“昨天结束、今天已不活跃”的订单
- 因此“昨天预估收益”不能只依赖 `GetFundingCredits(...)`
- 需要再补一个“历史 credit 查询”入口，用于找出结束时间是昨天的订单

#### A-1. 接口选型结论：昨天结束订单优先使用 Funding Credits History

经查官方 API 文档，`Funding Credits History` 更适合作为“昨天结束订单”的数据来源：

- 接口：`/v2/auth/r/funding/credits/{Symbol}/hist`
- 官方说明：`Inactive funds used in positions`
- 时间范围限制：**仅最近 3 天**

这个限制虽然不适合做长期收益统计，但**非常适合“昨天结束订单”**这个场景，因为需求只需要覆盖昨天这一日的失活 credit。

选择它而不是 ledger 的原因：

1. 它直接返回 funding credit 历史，语义和“昨天结束的借贷订单”一致
2. 它更适合做订单级计算，而不是金额流水级汇总
3. 最近 3 天的限制刚好覆盖昨天，不影响本需求

实现时的状态规则建议：

1. 先用 `Status` 过滤失活 credit
2. 再用历史记录里的更新时间字段判断是否落在“昨天”窗口内
3. 若接口返回样本和字段语义不完全一致，再按实际返回结果微调结束时间判定

#### A-2. 为什么不优先用 Funding Trades History

官方 `Funding Trades History` 接口：

- 接口：`/v2/auth/r/funding/trades/{Symbol}/hist`
- 定义：获取 funding trades / offered funding trades

它更偏“成交记录”视角，而不是 credit 生命周期视角。  
本需求要找的是：

- 哪些 credit 当前还活跃
- 哪些 credit 在昨天结束
- 这些 credit 在昨天窗口内活跃了多少秒

因此第一版不建议把 `Funding Trades History` 作为主数据源，否则后续要做 credit 级重建会更绕。

#### B. 实际到账收益

需要新增：

- Bitfinex ledger 历史查询接口
- 按时间范围过滤 funding wallet 利息记录
- 按统计窗口聚合金额

初步判断第一版要支持：

- 指定起止时间拉取 ledger
- 从 ledger 中筛选“利息收益”类型
- 聚合出：
  - 昨日
  - 最近 7 天
  - 本周
  - 本月
  - 本年

#### B-1. 接口选型结论：实际到账收益优先使用 Ledgers

经查官方 API 文档，`Ledgers` 更适合作为“实际到账收益”的主数据源：

- 接口：`/v2/auth/r/ledgers/{Currency}/hist`
- 支持：
  - `start`
  - `end`
  - `wallet`
  - `category`
- 官方说明：**最多可返回 6 年历史**

这几个特点决定了它非常适合做：

1. 昨日实际到账收益
2. 最近 7 天汇总
3. 本周 / 本月 / 本年汇总

也就是说：

- **订单级昨日预估收益** 用 `Funding Credits History`
- **实际到账收益汇总** 用 `Ledgers`

这两类需求不建议强行用一个接口统一解决。

## 手续费处理初步建议

当前已明确平台抽取收益 `15%` 作为手续费，因此初步方案先按固定值处理：

- 手续费比例 = `0.15`
- 实际到账前乘数 = `0.85`

后续如果你希望把它做成配置项，再决定是否抽成：

- 固定常量
- 配置项 `FUNDING_FEE_PERCENT`
- 自动读取平台 fee

## 调度设计初步建议

### 1. 调度方式

参考现有 `scheduleHourlyRateCheck()` 的写法：

- 每轮计算“下一个 09:35”
- `time.After(delay)`
- 到点执行一次
- 然后重新计算下一次

这样比固定 ticker 更适合“每天固定时刻”的语义。

### 2. 与现有任务的互斥

收益报告任务建议新增一个执行入口，例如：

- `executeDailyEarningsReport()`

并且要与：

- `MainTask`
- `LendingCheck`

共用互斥保护。

初步建议：

- 在 `Application` 增加 `earningsReportRunning`
- 由 `mainTaskMu` 统一保护
- 收益报告执行时禁止与 `MainTask` / `LendingCheck` 并发

### 3. 与 HourlyRateCheck 的关系

`HourlyRateCheck` 现在是公开数据检查，不一定需要纳入同一套互斥。  
但收益报告会访问私有 API，所以必须纳入互斥。

## 去重与持久化状态设计

建议扩展 `data.json`，增加类似：

- `daily_earnings.last_report_date`
- `daily_earnings.last_report_at`

用途：

1. 如果服务在 `09:35` 之后重启，不会重复发送
2. 如果收益报告已成功发送，再次触发时可跳过
3. 后续可扩展成“上次发送摘要”或“补发状态”

## Telegram 消息结构初步建议

建议一条消息分三块：

### 1. 标题与时间

- 每日收益报告
- 生成时间

### 2. 昨日收益对比

- 活跃订单数（参与昨日预估的订单数）
- 活跃/昨日结束订单总金额
- 昨天预估收益
- 昨日实际到账收益
- 预估与实际的差额

### 3. 汇总数据

- 最近 7 天
- 本周
- 本月
- 本年

### 4. 备注说明

明确说明：

- 预估收益口径是“昨天时间窗口内的理论收益”
- 昨日实际到账收益基于 Bitfinex ledger 汇总
- 汇总数据同样基于 Bitfinex ledger 汇总

这样用户不会把两个数误认为完全相等。

## 推荐的第一版范围

为了尽快得到稳定可用版本，建议第一版只做：

1. 每日 `09:35` 自动发送
2. 活跃借贷昨天预估收益
3. ledger 实际到账收益：
   - 昨日（用于和昨天预估收益对比）
   - 最近 7 天
   - 本周
   - 本月
   - 本年
4. `data.json` 去重
5. 与主任务 / 借贷检查互斥

## 第一版暂不建议做的内容

1. 自动读取 Bitfinex 手续费
2. `/earnings` 手动查询 Telegram 命令
3. 多币种联合汇总
4. 图表/CSV 导出
5. 补发历史收益报告
6. 数据库化持久化

这些都可以等第一版稳定后再扩展。

## 需要逐点确认的讨论项

下面这些点建议逐项确认，再更新最终方案：

### 1. 手续费来源

候选：

- A. 固定 `15%`
- B. 配置项 `FUNDING_FEE_PERCENT`
- C. 自动读取 summary API

当前建议：先选 A

### 2. 收益报告去重策略

候选：

- A. 每日只发一次，成功后记账
- B. 支持失败重试但仍保证当日不重复

当前建议：先做 A，失败仅记录日志，不自动补发

### 3. 冲突处理策略

候选：

- A. 与主任务/借贷检查冲突时直接跳过本次收益报告
- B. 冲突时延后几分钟重试一次

当前建议：更倾向 B，但实现复杂度略高，需要讨论

### 4. Telegram 展示格式

候选：

- A. 普通文本
- B. aligned 对齐格式

当前建议：如果 `NOTIFICATION_FORMAT=aligned`，则收益报告也跟随 aligned

### 5. 统计时区

候选：

- A. 服务器本地时区
- B. 固定 Asia/Shanghai
- C. 配置项控制

当前建议：直接按服务器本地时区执行；当前环境对应 `CST +0800`，因此北京时间 `09:35` 无需再换算。
